01

The Problem: Race Condition FROM VIDEO

Video ka setup: Counter class + 2 threads, ek hi shared object. Result hamesha 2000 aana chahiye... par aata kyun nahi?

Setup (video wala)

Counter.java + Test.java
class Counter {
    private int count = 0;

    public void increment() {
        count++;                        // 1000 baar call hoga har thread se
    }

    public int getCount() { return count; }
}

class MyThread extends Thread {
    private Counter counter;
    public MyThread(Counter counter) { this.counter = counter; }

    @Override
    public void run() {
        for (int i = 0; i < 1000; i++) counter.increment();
    }
}

public class Test {
    public static void main(String[] args) throws InterruptedException {
        Counter counter = new Counter();   // EK hi object — shared!
        MyThread t1 = new MyThread(counter);
        MyThread t2 = new MyThread(counter);
        t1.start(); t2.start();
        t1.join(); t2.join();                // dono khatam hone tak wait — phir hi print
        System.out.println(counter.getCount());
    }
}
  • Expectation: 1000 + 1000 = 2000
  • Reality: 1846, 1764, kabhi kabhi 2000 — har run pe alag!

Kyun hota hai? — count++ ki sachchai

count++ ek line hai, par 3 operations hain: read count → increment → write back.

  • Maan lo count ki value 101 hai
  • t1 ne 101 read kiya... usi waqt t2 ne bhi 101 read kiya (dono ko same mila!)
  • t1 ne 102 likha, t2 ne bhi 102 likha — 2 increments hue par value sirf 1 badhi
  • Jab aisa "collision" hua, ek increment lost — isliye 2000 se kam milta hai

Do threads ki timing aapas mein takra gayi (race lagayi) — isliye result unpredictable. Kabhi 2000 mila kyunki us run mein kahani takrayi hi nahi.

02

The Fix: synchronized FROM VIDEO

1. Synchronized Method

Counter.java — FIXED
class Counter {
    private int count = 0;

    public synchronized void increment() {  // ← bas yeh keyword!
        count++;
    }
}
  • Ab ek time pe EK hi thread increment() chala sakta hai
  • Jab ek thread andar hai, doosra wait karta hai — pehla nikle tabhi doosra andar jaata hai
  • Result: HAMESHA 2000 — guaranteed, har run pe

2. Synchronized Block

Agar poora method synchronize nahi karna, sirf critical part karna hai:

Alternative
public void increment() {
    // ...other non-critical kaam...
    synchronized (this) {          // sirf ye block lock hota hai
        count++;
    }
    // ...other non-critical kaam...
}
  • this ka matlab: jis instance pe method call hua hai uska lock
  • Multiple objects hain toh unki kahani independent chalegi — har object ka apna lock
  • Benefit: non-critical code parallel chalta rahega, sirf critical section serial
03

Terminology — 4 Terms FROM VIDEO

Interview ke liye ye 4 terms yaad rakho — sab isi ek example se aate hain.

⚠️ Race Condition
Multiple threads shared resource pe kaam kar rahe hain aur unki timing aise overlap ho gayi ki result unpredictable ho gaya (1846 wali problem)
🔒 Critical Section
Program ka wo part jahan shared resource access/modify hota hai — yahan count++ wala method. Ise "dhyaan se" (critically) handle karna hota hai
🤝 Mutual Exclusion
Mutual (threads ke beech ka rishta) + Exclusion (rokna) = ek time pe sirf ek thread critical section access kar sake. synchronized se achieve hota hai
🎯 The Goal
Race condition ko synchronized se hatao → mutual exclusion ensure karo → predictable result (hamesha 2000)

Ek line mein: shared resource + multiple threads = race condition. Fix = synchronized (mutual exclusion) on critical section.

Variation 1: Bank Account BONUS PRACTICE

Same concept, real-world scenario — pehle khud predict karo, phir answer dekho.

BankAccount.java
class BankAccount {
    private double balance = 1000;

    public void withdraw(double amount) {
        if (balance >= amount) {              // check
            balance = balance - amount;         // aur update — DANGER!
        }
    }
    public double getBalance() { return balance; }
}

Scenario: Account mein ₹1000 hai. Do threads simultaneously ₹800 withdraw karte hain.

  • Expected (single-thread logic): pehla withdrawal chal jata (1000-800=200), doosra fail hota (200 < 800)
  • Race condition mein kya hoga? Dono ne ek saath balance >= 800 check kiya — dono ko true mila (balance abhi bhi 1000 hai!) — dono ne withdraw kar diya
  • Result: -600 balance! Bank gaya, concept samajh gaya 😄

Fix: public synchronized void withdraw(...) — ab check+update atomic ho jayega, ek time pe ek thread. Doosra thread tab check karega jab balance already 200 ho chuka hoga → withdrawal reject.

Note: yahan critical section = check + update dono milake. Agar sirf update synchronized ho aur check nahi, toh bhi race rahegi — pura "check-then-act" sequence lock hona chahiye!

05

Variation 2: Movie Tickets BONUS PRACTICE

Isme synchronized BLOCK ka real use case hai — poora method nahi, sirf critical part.

BookMyShow.java
class TicketBooking {
    private int seatsAvailable = 2;              // sirf 2 seats!
    private Object lock = new Object();

    public void bookSeat(String user) {
        System.out.println(user + " booking dekh raha hai...");  // slow UI ka kaam
        try { Thread.sleep(100); } catch (Exception e) {}      // network delay

        synchronized (lock) {                      // CRITICAL PART only
            if (seatsAvailable > 0) {
                System.out.println(user + " ne seat le li! 🎟️");
                seatsAvailable--;
            } else {
                System.out.println(user + " ke liye koi seat nahi 😢");
            }
        }
    }
}

3 threads (Amit, Priya, Rahul) ek saath book karte hain, sirf 2 seats hain:

  • Bina synchronized: teeno ne seatsAvailable > 0 ek saath check kiya, teeno ko 2 dikha, teeno ne book kar liya — 2 seats mein 3 bookings! Overbooking 🚨
  • Synchronized block ke saath: booking decision (check + decrement) serial hota hai — pehle do ko seat, teesre ko "koi seat nahi"
  • Upar wala "network delay" wala code lock ke bahar hai — isliye wo part parallel chalta rahega, performance bhi achhi

Isi liye synchronized block usefUL hai: jitna chhota critical section, utna better performance — lock sirf zaroori jagah.

Predict the Output BONUS

Test.java
Counter c1 = new Counter();   // synchronized increment()
Counter c2 = new Counter();   // ALAG object!

MyThread t1 = new MyThread(c1);  // c1 pe 1000 increments
MyThread t2 = new MyThread(c2);  // c2 pe 1000 increments
t1.start(); t2.start();
t1.join(); t2.join();
System.out.println(c1.getCount() + " " + c2.getCount());
Answer: B — do ALAG objects hain, koi sharing hi nahi hai! Har counter apne apne 1000 increments karega. (Agar same object hota, tab synchronized kaam aata — race ki wajah se hi toh problem hoti hai.) Locks per-object hote hain — different objects = different locks = koi conflict nahi, koi zaroorat bhi nahi.
