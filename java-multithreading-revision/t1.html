Locking: The Foundation FROM VIDEO

The notebook analogy from the video — three kids, one notebook, no supervisor.

The analogy

  • Notebook = shared resource. Three kids = three threads (t1, t2, t3)
  • Without any rule: everyone writes at once → jumbled, unreadable mess
  • With synchronized: only one kid writes at a time — whoever holds access puts a "lock" on it
  • When that kid finishes (or the teacher/scheduler switches turns), the lock passes to the next thread

This is exactly what the synchronized keyword was doing in the Counter example — locking the shared resource so only one thread accesses it at a time.

Two types of locks

Intrinsic (Implicit)Explicit (Manual)
What it isBuilt into every Java object — invisible, always thereA Lock object you create yourself
How to useJust use the synchronized keyword — lock/unlock happen automaticallyCall lock() / unlock() yourself
ControlNone — no control over who goes first, how long anyone holds itFull control — when to lock, when to unlock, timeouts, attempts
Advanced—tryLock with timeout, interruptible waiting, reentrancy

synchronized automatic hai — lekin control zero. Explicit locks give you the steering wheel.

The Problem with synchronized FROM VIDEO

The bank account example — where synchronized breaks down.

The setup

BankAccount.java
class BankAccount {
    private int balance = 100;
    private final Lock lock = new ReentrantLock();  // later — first version uses synchronized

    public synchronized void withdraw(int amount) {
        System.out.println(Thread.currentThread().getName() + " attempting withdrawal " + amount);
        if (balance >= amount) {
            System.out.println(Thread.currentThread().getName() + " proceeding with withdrawal");
            try {
                Thread.sleep(3000);          // simulates a slow DB transaction
            } catch (InterruptedException e) { }
            balance -= amount;
            System.out.println(Thread.currentThread().getName() + " completed withdrawal. Remaining: " + balance);
        } else {
            System.out.println(Thread.currentThread().getName() + " insufficient balance");
        }
    }
}
  • Two threads, same account (₹100), both withdraw ₹50
  • t1 acquires the synchronized lock and enters the 3-second "transaction"
  • t2 is now blocked — waiting indefinitely

The core issue: indefinite waiting

lock held — transaction (3s)
Thread-2

0s3s6s
  • That sleep simulates a database call — normally 3 seconds, but on a bad day it could take 10 seconds, an hour, anything
  • t2 has no timeout, no clue, no escape — it just waits forever
  • synchronized gives you zero control over this: who goes first, how long they hold the lock — nothing

Washroom analogy from the video: the guy inside says "it will take time" — the guy outside has no option but to stand there indefinitely. That's the problem to fix.
