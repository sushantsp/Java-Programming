Locking: The Foundation FROM VIDEO

The notebook analogy from the video — three kids, one notebook, no supervisor.

The analogy

  • Notebook = shared resource. Three kids = three threads (t1, t2, t3)
  • Without any rule: everyone writes at once → jumbled, unreadable mess
  • With synchronized: only one kid writes at a time — whoever holds access puts a "lock" on it
  • When that kid finishes (or the teacher/scheduler switches turns), the lock passes to the next thread

This is exactly what the synchronized keyword was doing in the Counter example — locking the shared resource so only one thread accesses it at a time.

Two types of locks

Intrinsic (Implicit)Explicit (Manual)
What it isBuilt into every Java object — invisible, always thereA Lock object you create yourself
How to useJust use the synchronized keyword — lock/unlock happen automaticallyCall lock() / unlock() yourself
ControlNone — no control over who goes first, how long anyone holds itFull control — when to lock, when to unlock, timeouts, attempts
Advanced—tryLock with timeout, interruptible waiting, reentrancy

synchronized automatic hai — lekin control zero. Explicit locks give you the steering wheel.

The Problem with synchronized FROM VIDEO

The bank account example — where synchronized breaks down.

The setup

BankAccount.java
class BankAccount {
    private int balance = 100;
    private final Lock lock = new ReentrantLock();  // later — first version uses synchronized

    public synchronized void withdraw(int amount) {
        System.out.println(Thread.currentThread().getName() + " attempting withdrawal " + amount);
        if (balance >= amount) {
            System.out.println(Thread.currentThread().getName() + " proceeding with withdrawal");
            try {
                Thread.sleep(3000);          // simulates a slow DB transaction
            } catch (InterruptedException e) { }
            balance -= amount;
            System.out.println(Thread.currentThread().getName() + " completed withdrawal. Remaining: " + balance);
        } else {
            System.out.println(Thread.currentThread().getName() + " insufficient balance");
        }
    }
}
  • Two threads, same account (₹100), both withdraw ₹50
  • t1 acquires the synchronized lock and enters the 3-second "transaction"
  • t2 is now blocked — waiting indefinitely

The core issue: indefinite waiting

  • That sleep simulates a database call — normally 3 seconds, but on a bad day it could take 10 seconds, an hour, anything
  • t2 has no timeout, no clue, no escape — it just waits forever
  • synchronized gives you zero control over this: who goes first, how long they hold the lock — nothing

Washroom analogy from the video: the guy inside says "it will take time" — the guy outside has no option but to stand there indefinitely. That's the problem to fix.

The Lock Interface & ReentrantLock FROM VIDEO

Manual locking with full control — the method set.

Creating a Lock

BankAccount.java
private final Lock lock = new ReentrantLock();
  • Lock is an interface — you can't instantiate it directly
  • ReentrantLock is the implementation class (why it's called "reentrant" — section 05)
  • Every Java object already has an intrinsic lock (used by synchronized) — here we create our own lock object
  • Whichever thread acquires this lock gets access to the critical section

Key-and-lock mental model: lock() = taking the key. Whoever holds the key enters; others must wait or leave.

The four core methods

MethodBehaviourReturns / Throws
lock() Acquires the lock — waits indefinitely until available (same behaviour as synchronized — no real advantage) void
tryLock() Tries immediately — no waiting at all. If the lock is free → acquire it. If not → walk away true if acquired, false if busy
tryLock(1, TimeUnit.SECONDS) Waits up to the given time for the lock. Free within 1s → acquire. Timeout → walk away true / false — throws InterruptedException (because it waits)
unlock() Releases the lock — always call in finally void
lockInterruptibly() Like lock() (waits indefinitely) — but the waiting thread can be interrupted from outside throws InterruptedException

tryLock = "knock once, if busy leave". tryLock(time) = "I'll wait 1 second, not more". lock() = "main yahin khada rahunga" — no benefit over synchronized.

Why tryLock(1, SECONDS) throws InterruptedException

Plain tryLock() doesn't wait — so nothing can interrupt it. But tryLock(time) waits, and while waiting, another thread could interrupt it. Any method that waits can be interrupted — so the exception must be handled (try-catch or throws).

The Fix: Bank Account with tryLock FROM VIDEO

Full code

BankAccount.java
class BankAccount {
    private int balance = 100;
    private final Lock lock = new ReentrantLock();

    public void withdraw(int amount) {
        System.out.println(Thread.currentThread().getName() + " attempting withdrawal " + amount);

        try {
            if (lock.tryLock(1000, TimeUnit.MILLISECONDS)) {   // wait max 1s
                try {
                    if (balance >= amount) {
                        System.out.println(Thread.currentThread().getName() + " proceeding with withdrawal");
                        Thread.sleep(3000);                       // slow transaction
                        balance -= amount;
                        System.out.println(Thread.currentThread().getName()
                            + " completed. Remaining: " + balance);
                    } else {
                        System.out.println(Thread.currentThread().getName() + " insufficient balance");
                    }
                } finally {
                    lock.unlock();                                // ALWAYS in finally!
                }
            } else {
                System.out.println(Thread.currentThread().getName()
                    + " could not acquire the lock — will try later");
            }
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();                  // restore interrupt status
        }
    }
}
Output
Thread-1 attempting withdrawal 50
Thread-2 attempting withdrawal 50
Thread-1 proceeding with withdrawal
Thread-2 could not acquire the lock — will try later
(after 3s...)
Thread-1 completed. Remaining: 50
  • Thread-1 acquires the lock, starts its 3-second transaction
  • Thread-2 tries for 1 second — fails — prints "will try later" and moves on instead of blocking forever
  • unlock() sits in finally — even if an exception hits, the lock is released (that's what finally is for: releasing resources)
  • Note the structure: outer try-catch for tryLock's InterruptedException, inner try-finally for the work + unlock

Why "Reentrant"? FROM VIDEO

The outer/inner puzzle from the video — and the counting mechanism that solves it.

The puzzle

ReentrantExample.java
class ReentrantExample {
    private final Lock lock = new ReentrantLock();

    public void outer() {
        lock.lock();                 // main thread acquires (count: 1)
        System.out.println("outer method");
        inner();                     // calls inner... which locks AGAIN
        lock.unlock();               // (count: 0)
    }

    public void inner() {
        lock.lock();                 // same lock, same thread! (count: 2)
        System.out.println("inner method");
        lock.unlock();               // (count: 1)
    }
}
  • outer() locks → inner() tries to lock the same lock again from the same thread
  • With a naive lock this would be a self-deadlock: inner waits for outer to release... but outer can't finish until inner returns. Circular dependency!
  • But ReentrantLock works fine. Why? A thread can re-enter a lock it already holds

The counting mechanism — interactive

ReentrantLock maintains an internal hold count. Play it step by step:

Start
—
→
outer: lock()
0
→
inner: lock()
0
→
inner: unlock()
0
→
outer: unlock()
0

The rules that follow

  • Every lock() must be paired with an unlock() — the lock fully releases only when the count drops back to zero
  • One extra unlock (count goes below zero) → IllegalMonitorStateException
  • Don't unlock in inner and continue working in outer — count hits zero early, another thread can sneak in mid-operation (inconsistency!)
  • synchronized is ALSO reentrant — reentrancy isn't exclusive to ReentrantLock; it's the extra control that makes Lock worth using

House key analogy: you hold the main key, so you can enter any room — washroom, bedroom, anywhere. Each entry/exit pairs up; only the final exit locks the house.

Critical Practices FROM VIDEO

1. unlock() always in finally

If an exception fires between lock() and unlock(), the lock never releases — every other thread blocks forever. finally guarantees release, exception or not.

2. Restore the interrupt status in catch

Good practice
catch (InterruptedException e) {
    Thread.currentThread().interrupt();   // restore the interrupt status
}
  • Catching InterruptedException and only logging it counts as ignoring it — the thread's "I was interrupted" status is lost
  • Calling Thread.currentThread().interrupt() restores that flag, so monitoring/cleanup code that checks isInterrupted() still works
  • Risk of an empty catch: delayed shutdown and lost information — the thread was interrupted mid-task and nobody finds out

3. Thread states during locking BONUS RECAP

SituationState
lock() / lockInterruptibly() waitingBLOCKED / WAITING — waits indefinitely
tryLock(time) waitingTIMED_WAITING — waits up to the timeout
tryLock() busyNo wait at all — returns false immediately

Now the BLOCKED/WAITING states from the lifecycle video finally have a real cause to point at — lock contention.

LX 1 Your First Manual Lock EASY
Task: Create a class Counter with an int field and an increment() method. Use a ReentrantLock to protect the increment — lock() at the start, unlock() in finally. Launch 2 threads doing 100,000 increments each; verify the final count is always 200,000.
Expected output (every run)
Count: 200000
Structure: private final Lock lock = new ReentrantLock(); → in increment(): lock.lock(); try { count++; } finally { lock.unlock(); } — the try-finally is the whole point of this exercise.
Lx1.java
import java.util.concurrent.locks.Lock;
import java.util.concurrent.locks.ReentrantLock;

class Counter {
    private int count = 0;
    private final Lock lock = new ReentrantLock();

    public void increment() {
        lock.lock();
        try {
            count++;
        } finally {
            lock.unlock();     // ALWAYS in finally
        }
    }
    public int getCount() { return count; }
}
LX 2 Timed tryLock — The Bank Scenario MEDIUM
Task: Recreate the video's bank scenario. A withdraw(amount) method: acquire the lock with tryLock(1, TimeUnit.SECONDS). If acquired → check balance, simulate a 3-second transaction (sleep), deduct. If not acquired within 1s → print "could not acquire the lock, will try later" and return without waiting. Two threads withdraw 50 from a balance of 100.
Expected output
Thread-1 proceeding with withdrawal
Thread-2 could not acquire the lock, will try later
(3s later) Thread-1 completed. Remaining: 50
tryLock(1, TimeUnit.SECONDS) returns boolean — branch on it. The InterruptedException from the timed tryLock needs an outer try-catch. Inside the if-branch, use an inner try-finally: work in try, unlock in finally. Don't forget to print the thread name using Thread.currentThread().getName().
Lx2.java
import java.util.concurrent.TimeUnit;
import java.util.concurrent.locks.*;

class BankAccount {
    private int balance = 100;
    private final Lock lock = new ReentrantLock();

    public void withdraw(int amount) {
        String name = Thread.currentThread().getName();
        try {
            if (lock.tryLock(1, TimeUnit.SECONDS)) {
                try {
                    if (balance >= amount) {
                        System.out.println(name + " proceeding");
                        Thread.sleep(3000);
                        balance -= amount;
                        System.out.println(name + " completed. Remaining: " + balance);
                    } else {
                        System.out.println(name + " insufficient balance");
                    }
                } finally {
                    lock.unlock();
                }
            } else {
                System.out.println(name + " could not acquire the lock, will try later");
            }
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }
}
LX 3 Reentrancy Proof + Breaking It HARD
Task: Part A: Write outer() and inner() methods — outer locks, prints, calls inner; inner locks the same lock again, prints, unlocks. Run it — verify reentrancy works (no deadlock). Part B: Now deliberately add one extra unlock() at the end of outer(). Catch the exception that gets thrown and print its name.
Expected output
Part A: outer method → inner method (works fine!)
Part B: java.lang.IllegalMonitorStateException
Part A: lock() twice + unlock() twice = count 1→2→1→0, clean release. Part B: with an extra unlock the count would go below zero — wrap the outer() call in try-catch in main and print e. The lock pairs up like entering and exiting a room: each entry needs its own exit.
Lx3.java
public class Lx3 {
    private final Lock lock = new ReentrantLock();

    void outer() {
        lock.lock();                    // count: 1
        System.out.println("outer method");
        inner();                         // count: 2 → back to 1
        lock.unlock();                   // count: 0 — released
        lock.unlock();                   // Part B: EXTRA! count: -1 → EXCEPTION
    }

    void inner() {
        lock.lock();                    // re-entry — same thread, allowed
        System.out.println("inner method");
        lock.unlock();
    }

    public static void main(String[] args) {
        try {
            new Lx3().outer();
        } catch (Exception e) {
            System.out.println("Caught: " + e);
        }
    }
}
LX 4 Why finally Matters — Leak a Lock on Purpose HARD
Task: Write a method that locks, then throws a RuntimeException inside the critical section, with unlock() placed AFTER the throwing line (not in finally). Call it from t1, catch the exception in main. Then start t2 which calls a normal locked method — observe that t2 waits forever (run it, watch it hang, then stop it). Fix it by moving unlock() into finally and verify both threads complete.
Expected output (broken version — program HANGS)
t1: entered critical section
Exception in t1 (lock leaked!)
t2: waiting for lock... (forever — press stop)

=== fixed with finally ===
t1: exception handled, lock released
t2: acquired lock, done
Give t2 a short sleep before it tries, so t1's exception happens first. For the fixed version the structure is: lock.lock(); try { work that may throw } finally { lock.unlock(); } — the finally runs even during exception propagation, which is exactly why the idiom exists.
Lx4.java
public class Lx4 {
    private final Lock lock = new ReentrantLock();

    void brokenMethod() {
        lock.lock();
        System.out.println("t1: entered critical section");
        throw new RuntimeException("boom");
        // unlock() here would be unreachable — lock LEAKED
    }

    void fixedMethod() {
        lock.lock();
        try {
            System.out.println("t1: entered critical section");
            throw new RuntimeException("boom");
        } finally {
            lock.unlock();             // runs even during the exception!
        }
    }

    public static void main(String[] args) throws InterruptedException {
        Lx4 obj = new Lx4();

        Thread t1 = new Thread(() -> {
            try { obj.fixedMethod(); } catch (Exception e) {
                System.out.println("t1 exception handled, lock released");
            }
        });
        Thread t2 = new Thread(() -> {
            obj.lock.lock();
            try { System.out.println("t2: acquired lock, done"); }
            finally { obj.lock.unlock(); }
        });

        t1.start();
        Thread.sleep(500);              // let t1 finish (incl. exception) first
        t2.start();
        t1.join(); t2.join();
    }
}
Swap fixedMethod() for brokenMethod() to watch the hang — t2 blocks forever because the leaked lock is never released. This is why every ReentrantLock tutorial drills the finally idiom.
